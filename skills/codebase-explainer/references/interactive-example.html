shop-platform

A shopping system built from 4 small services — learn it by clicking through

This is a system that lets people shop online. Someone creates an account, logs in, buys what's in their cart — and gets a confirmation email when the order goes through. It's not one program: four small parts talk to each other. Below, you'll first drive the order's journey step by step yourself, then test whether you really got it with a few questions.

Technical details

A real bug: the note dropped in the mailbox contains Alice's user ID but no email address. The line to: order.userId in notifications/src/templates/orderConfirmation.js treats that ID as an email — verified with grep against the code; the mail most likely never sends.

Fragile spot: if the order is written to the DB but dropping the note into the mailbox fails, there is no rollback — you can end up with an order in the DB and no event ever published. Relevant code: orders/src/services/orderService.js

Test yourself — 3 questions
1. Suppose the notifications service is completely down. Alice clicks "Buy". What happens?
Correct: the order succeeds. orders just drops a note in the mailbox and immediately says "received" — it never knows whether notifications is alive. The two are fully independent.
2. auth rotates its JWT_SECRET, but orders keeps the old value. What happens?
Correct: auth signs wristbands with the new secret, orders checks them with the old one — signatures don't match, so all new tokens are rejected. This is the one secret the two services share; it must be rotated together.
3. A "my email never arrived" complaint comes in. Which service do you look at first?
Correct: email is entirely notifications' job; gateway and auth have nothing to do with mail. (Bonus: this project genuinely has an email bug — see "Technical details" above.)
How login / registration works

The auth service is the ID-card office: on registration it hashes and stores the password, on login it checks the password and hands out a JWT.

Think of the JWT as an event wristband — once you're checked and banded, no one asks for your ID at every door, but the band expires (here: 2 hours) and you need a new one.
Technical details

The token is signed in auth/src/services/authService.js with expiresIn: '2h'; verification lives in orders/src/services/authMiddleware.js. Passwords are hashed with bcrypt (10 rounds); plaintext is never stored.

How to run it

Each service installs with npm install in its own folder; a running PostgreSQL and RabbitMQ are required for all of them.

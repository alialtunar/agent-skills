What does this system do?

It lets people shop online: create an account, log in, buy what's in the cart, receive a confirmation email. It is not one program — four small services talk to each other, and the most interesting conversations happen after the customer has already left.

The essence in one sentence

The synchronous path (gateway → auth → orders) answers the customer fast; everything slow or optional (email) is handed to a queue and happens in the background.

Think of the queue as the ticket rail in a restaurant kitchen: the waiter pins the order and walks back to the table — never waiting to see when the kitchen picks it up.

On stage: a gateway (front door, no logic of its own), an auth service (issues signed JWT "wristbands"), an orders service (writes the order, publishes an event), and a notifications worker that is not a web server at all — it just listens to the queue and sends mail.

The gateway — a front door with no opinions

services/gateway/src/index.js
app.use("/auth",   createProxyMiddleware({ target: AUTH_URL }));
app.use("/orders", createProxyMiddleware({ target: ORDERS_URL }));

That is the entire service: match the path, forward untouched. Keeping the door dumb means auth and orders can change freely behind it.

The wristband check — stateless auth

services/orders/src/services/authMiddleware.js
const token = (req.headers.authorization || "").split(" ")[1];
req.user = jwt.verify(token, process.env.JWT_SECRET);
next();  // invalid/expired → catch → 401, handler never runs

orders never calls the auth service — it only checks the signature. The catch: auth (signer) and orders (verifier) must share the same JWT_SECRET; rotate one without the other and every token dies.

Write, then publish — and why that order matters

services/orders/src/services/orderService.js
const order = await repo.insert(userId, items);   // DB first: we need the real id
await publishOrderCreated(order);                 // then the event carries it
return order;

DB-first so the event carries the real order.id. Fragile spot: if the publish throws after the insert, there is no rollback — order exists, event never sent. A worthwhile fix would be an outbox pattern.

Fire and forget — the customer never waits for mail

services/orders/src/events/publisher.js
ch.publish("orders", "", Buffer.from(JSON.stringify({
  type: "order.created", order   // note: carries userId, no email…
})));

orders drops the note and replies 201 immediately. It doesn't know notifications exists — and can't know if nobody is listening. Look closely at the payload: it carries a userId, and nothing else about Alice. Remember that.

The listener — a worker, not a server

services/notifications/src/workers/orderCreatedWorker.js
const q = await ch.assertQueue("", { exclusive: true }); // unnamed → not durable!
ch.consume(q.queue, async (msg) => {
  const event = JSON.parse(msg.content.toString());
  if (event.type === "order.created") await sendOrderConfirmation(event.order);
  ch.ack(msg);  // acked even on unknown types — no retry path
});

Two quiet risks: the queue is exclusive and unnamed, so messages arriving while the worker is down are lost forever; and everything is acked, so a failed send is never retried.

The payoff — a real bug you can only see end to end

services/notifications/src/templates/orderConfirmation.js
await transporter.sendMail({
  to: order.userId,   // ← this is a user id, not an email address!
  subject: "Your order is confirmed"
});

Step 5's payload carried only userId. Read alone, each service looks fine; traced end to end, the mail goes "to 42" and silently fails. This is why the simulation follows the data, not just the arrows.
